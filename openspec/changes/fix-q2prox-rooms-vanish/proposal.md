## Why

Тестеры rc17 на Windows раз в 1–3 дня видят пустой список «Custom» в Q2PRO-X около часа. По коду есть две достаточные причины и одна открытая: любая одна невалидная или дублирующая строка в `room/get` или алиас в `/lookup` роняет **всё** обновление каталога (H4, отчёт §0.2 a–d), а цель, исчерпавшая лимит восстановления, остаётся тупиком до перезапуска (H1, §0.6). Подтвердить, какая из них действует у тестеров, нечем: лаунчер пишет диагностику только в stderr, координатор Windows и шлюз — чёрные ящики (§0.7). Поэтому сначала данные (ловушка, логи), затем поведение.

## What Changes

В порядке исполнения (отчёт §6):

- **A. Ловушка H4 на неизменённом rc17 + сбор логов тестеров** — вне репозитория, `noncommit/q2prox-h4-trap/`: ежеминутный GET `room/get` и `/lookup` с вердиктом **того же** `catalog.ps1`/`q2dz-launch.ps1` rc17 под pwsh, совещательные проверки парсера (дубликаты ключей точные и по регистру), сводка эпизодов. `rtc/servers` только в памяти. Тестеры продолжают `Run-Log.cmd` по tester-guide, вопрос 3 которого уточняется («не закрывая Q2prox, подождать и нажать Refresh»).
- **B. Диагностика (отчёт §5).** Файл `logs/q2dz.log` с одним писателем (лаунчер), дренаж stderr координатора через очередь, ротация 2 × 5 МБ, события `SESSION`/`TARGET`/`GATEWAY` координатора и `CATALOG_ROW` лаунчера в формате `TS COMPONENT EVENT key=value`, безопасная категория ошибки и HTTP-статус в `CATALOG_REFRESH`, таблица событий и грамматика значений в спеке, `docs/LOGGING.md`, правка tester-guide. `CATALOG_ROW` в B — только классификация строк (поведение rc17 не меняется: обновление по-прежнему падает), чтобы логи тестеров со сборкой B уже называли виновную строку. Чат — только заметка автору.
- **C. H4: терпимый гейт refresh (отчёт §2), обе ОС.** Отказ по строке, а не по телу. Три состояния строки: отсутствует → miss/DROP как сейчас; присутствует, но невалидна → пропущена для новых целей, живая цель удерживается с последним хорошим конфигом два успешных обновления (счётчик, как misses), затем DROP; конфликт идентичности (определяется до фильтра валидности) → группа пропущена, живая цель удерживается, замена не создаётся. `/lookup`: плохой алиас пропущен, дубликат схлопнут. «Только чужие игры» = пустой каталог. Отказы всего обновления (форма тела, `rtc/servers`, ICE, ёмкость, конфиг, content-check) не трогаются. Строгие валидаторы и кейсы `invalid-*`/`unsupported-*` не меняются; добавляется общий вид кейсов `refresh-scenario` в `tests/contracts/doszone-api-cases.json` для обоих раннеров.
- **D. H1: восстановление целей (отчёт §3), обе ОС — условно**, только по коррелированным логам B от тестеров (ловушка A координатор не наблюдает и H1 подтвердить не может): сброс `recovery_count` при READY, кулдаун 60 с по монотонному времени только для цели с исчерпанным бюджетом (`retry_not_before`), обычные повторы не задерживаются, идемпотентный terminal, игнор устаревших событий; lifecycle-матрицы расширяются с управляемым кулдауном; документация текущей политики (`windows/coordinator/README.md:55-57`, `linux/docs/ARCHITECTURE.md:108-112`, ADR 0004:155-161) обновляется вместе с D.
- **E. H10 (отчёт §4).** Офлайн Node-шаг на закреплённом WebRTC-NET `62fe52c` (`deps.lock.json:5`), артефакты сверяются по sha256 с `noncommit/q2prox-rc17-build/webrtc-release/webrtcnet.{mjs,wasm}` — без Cloud. Живой шаг с Create — **только по решению пользователя**.

**Один change вместо трёх (принятое отклонение от отчёта §6/§9 #19).** Постановка задачи задала один change с группами A–E. Диагностика (B), H4 (C) и условный H1 (D) — отдельные коммиты в одной ветке в этом порядке; B не зависит от C, C не зависит от D. Если D по данным не выполняется, delta-спека `q2prox-target-recovery` при архивации **не промотируется** в `openspec/specs/`, а группа D помечается «не подтверждено данными» в `D-decision.md`; завершение change без D допустимо.

Компромисс H4 (говорится прямо): удержание живой цели ограничено двумя успешными обновлениями. Если чужая строка остаётся невалидной дольше (≈30 с при штатной каденции), здоровый сервер получит DROP и переподключится после валидной строки. Это осознанно: «одна невалидная строка не роняет все остальные» гарантируется всегда, «не рвёт здоровый транспорт» — только на коротких сбоях.

Не меняется: ключи, различающиеся регистром (H4e) — парсер падает до валидатора, ждём ловушку; `transport_disabled` и остановленная страница транспорта (это H2); константы лимитов восстановления по ОС не выравниваются.

## Capabilities

### New Capabilities
- `q2prox-catalog-refresh`: обновление каталога комнат лаунчером: судьба строки по её состоянию, удержание живой цели при невалидной строке, санация `/lookup`, пустой каталог, общий контракт `refresh-scenario` для обеих ОС.
- `q2prox-session-logging`: журнал сессии q2prox-dz: файл, формат строки, события компонентов, категории ошибок, ротация, allow-list полей без секретов.
- `q2prox-target-recovery`: восстановление целей координатора после сбоя транспорта: пополнение бюджета на READY, кулдаун терминальной цели по времени, идемпотентность и игнор устаревших событий (вводится группой D, условно).

### Modified Capabilities
- нет: существующие спеки (`q2ded-dual-transport` и др.) лаунчер и координатор q2prox-dz не описывают.
