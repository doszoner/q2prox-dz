# Стабильный маршрут при обновлении карты и диагностика пустого Custom

## Проблема и доказательства

13 сентября 2026 native Q2PRO-X пережил смены карты на OpenFFA в 17:58:15 и 17:59:46 UTC и вновь вошёл в игру в 17:59:48. Затем launcher сообщил `CONTENT_READY q2dm1` в 18:01:44.310, сервер зарегистрировал reset игрока в 18:01:44.322, клиент — трёхсекундный таймаут в 18:01:47.284. Аналогичная цепочка есть в первом эпизоде 17:33:20 UTC.

Настоящий Linux planner при изменении только `map` формирует `DROP → PUT`; coordinator меняет target ID, gateway уничтожает старый loopback UDP endpoint. В локальном эксперименте старый endpoint перестал отвечать, новый отвечал. Исключение map из решения о пересоздании сохраняет endpoint. Windows planner воспроизводит тот же DROP.

Снимков каталога и ошибок refresh во время второго эпизода нет. Дополнительный просмотр локального journal за 17:33:40–18:02:00 UTC не обнаружил `CONTENT_MISSING` или `CONTENT_ERROR`. Поэтому отсутствие карты не доказано как причина задержки 118 секунд. Возможны задержка публикации карты, ошибка HTTP/валидации/lookup; различить их по старому журналу нельзя.

Для пустого списка есть конкретный дополнительный дефект Linux: `reconcile_targets` бросает исключение при одной отсутствующей карте, а первоначальный запуск подавляет его и публикует пустой набор. При refresh сохраняется предыдущий набор, включая пустой. Windows rc16 уже изолирует отсутствующую карту в рамках одной комнаты. Это воспроизводимый механизм, но не доказанная история исчезновения списка у владельца, версия его launcher и ответы каталога неизвестны.

На обеих платформах есть ещё один точный механизм частичного списка: `registered_rooms`/`Select-Q2DzRegisteredRooms` пересекают каталог с `/lookup`. Пустой или неполный список aliases является допустимым ответом; он может оставить только часть серверов без ошибки. Фильтра «показывать владельцу его комнаты» нет. Поэтому «только свои серверы» лучше всего соответствует неполному alias intersection, но без снимка lookup это гипотеза. Новые ready/registered counts отделят её от пустого каталога. Временное снятие endpoints при map-only DROP также само по себе уменьшает список до нового READY.

118 секунд не являются заданным таймером launcher: есть последовательные HTTP-запросы с пределом 15 секунд каждый и пауза 15 секунд после refresh, checker запускается синхронно без timeout. Readiness coordinator может задерживать появление endpoints, но не объясняет время предшествующего `CONTENT_READY`. Локальный пример room-agent настроен на отправку каждую секунду и stale 13 секунд; настройки чужого запущенного процесса архивом не подтверждены.

## Выбранное решение

Минимально исправить существующие launcher, не меняя coordinator, transport, HTTP/HUB schemas, настройки Q2 или сервисы DOS.Zone. Альтернатива — пересоздавать маршрут с принудительным переподключением Q2 — расширяет интерфейс и прерывает игру. Кэш каталога между запусками сохранял бы устаревшие targets и не устранял причину; не добавляем.

1. В Linux и Windows исключить только `map` и уже исключаемый `iceServers` из сравнения, решающего DROP. Полный актуальный config и проверенное имя карты сохраняются для будущего recovery. Alias/signaling/game/ordered и остальные поля продолжают участвовать в сравнении.
2. Сначала вычислить `map_changed` и проверить новую карту независимо от `changed`, затем принимать решение о пересоздании по транспортным полям. Доступная карта сохраняет живой target. Отсутствующая карта снимает только эту комнату; новые комнаты с отсутствующей картой пропускаются. Один row проверяется не более одного раза за планирование: после обработки существующей комнаты не проверять её повторно в цикле новых. В Linux привести поведение к уже принятому Windows rc16: код checker 0 означает доступность, только 3 — отсутствие; `OSError` и любой другой код (включая 64/70) преобразуются в `LaunchError`, сохраняющий прежний snapshot.
3. В обоих launcher добавить безопасный stderr-журнал одного refresh: UTC время, последний этап (`catalog`, `lookup`, `rtc`, `plan`), результат, длительность, число ready/registered/targets/drops при успехе; при ошибке — прежнее число targets. Никаких exception strings, JSON payload, URL с query, SDP или credentials. Успешный пустой каталог отличается от ошибки и от отфильтрованных aliases. Длительность измеряется монотонными часами. Существующие stdout/pipe протоколы не меняются.
4. При снятии/пропуске комнаты из-за отсутствующей карты писать безопасное событие с проверенными room ID и map. Двух успешных пропусков для удаления отсутствующей в каталоге комнаты, предела 256 и строгой валидации не менять.

## Контракты

ADR 0004 задаёт локальный HTTP source, запуск Q2 с пустым источником, индивидуальную готовность targets и ручной Refresh в Q2. Ошибка каталога сохраняет текущий snapshot. Эти правила сохраняются.

`docs/design/2026-09-03-dedicated-server-support.md`, раздел «Изменение карты», требует сохранять живой gateway при доступной новой карте и снимать endpoint при отсутствующей. Более поздний shared runtime содержит противоречащую этому строку: map включён в причины DROP. Настоящий дизайн явно заменяет только это внутреннее правило shared runtime: доступный map-only update сохраняет endpoint. Это и есть исправление диагностированного обрыва, реализация которого разрешена пользователем. Строку в `docs/design/2026-09-03-shared-multiroom-gateway.md` обновить вместе с кодом. ADR 0004 и wire-схемы не меняются. Исторические квоты 3+2 из dedicated-документа заменены shared runtime; не возвращаем их. План Windows rc16 от 8 сентября закрепляет изоляцию отсутствующей карты и сохранение snapshot при сбое checker.

Изменение имени карты — метаданные для проверки контента, а не новая transport identity. Реальные имя/карта/игроки в интерфейсе по-прежнему приходят из Quake status. Старый UDP endpoint сохраняется, пока транспортная конфигурация и сама комната сохраняются.

## Критерии приёмки и ограниченная проверка

- Изменение только карты вызывает content check, обновляет map/config и не формирует DROP на обеих платформах; ICE обновляется прежним отдельным heartbeat.
- Изменение transport identity продолжает формировать DROP. Отсутствующая карта исключает только соответствующую комнату; рабочая соседняя остаётся, а при появлении карты комната добавляется снова.
- Ошибка checker/HTTP/каталога не публикует разрушительный snapshot. При ошибке на старте Q2 всё ещё запускается; журнал объясняет этап отказа.
- Журнал позволяет отличить готовые строки от registered и запланированных targets, показывает длительность и UTC, не содержит специально внедрённого секретного маркера.
- Прогнать существующие Python launcher и PowerShell catalog tests с малыми регрессиями; один coordinator/UDP fixture с реальным planner проверяет сохранение старого endpoint. Настоящие WebRTC и Windows gameplay не объявлять проверенными.

## Поставка и откат

Изолированная ветка `fix_catalog_map_refresh` от `deee241ac0c4bc2c28646d4e387305fac94a9e72`. В scope входят три launcher-файла, существующие тесты, дизайн/план и итоговая проверка. Никаких новых зависимостей, фоновых сервисов, изменений сервера и release version. Пользователь разрешил реализацию и коммит; установка и публикация не запрошены. Откат — revert исходного fix-коммита; форматов и сохранённых данных нет.

## Design pre-mortem

Независимый technical-premortem: REVISE — сделать конкретными различие кодов checker и порядок map-check относительно transport comparison. Пункт 2 уточнён: 0/3/ошибка с нормализацией OSError, независимый map-check, отсутствие повторной проверки существующей комнаты. Эти правила проверяются тестами отсутствующей новой/существующей карты с рабочим соседом и кодов 3/64/70. Повторная сверка с приведёнными исходниками: PASS, блокирующего изменения ADR или публичного контракта нет.
