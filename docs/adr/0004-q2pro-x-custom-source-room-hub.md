# ADR 0004: комнаты Dos.Zone во встроенном server browser Q2PRO-X

- **Status:** Accepted for rc14 gateway-layer; full release acceptance pending
- **Date:** 2026-08-23
- **Related:** [Архитектура](../ARCHITECTURE.md),
  [ADR 0002](0002-launcher-owned-session-lifecycle.md),
  [ADR 0003](0003-linux-managed-session-and-guardian.md)

## Контекст

Предыдущая поставка показывала комнаты в отдельном launcher, поднимала один
gateway и запускала Q2PRO-X с
`+set game 3zb2 +connect 127.0.0.1:<port>`. Пока Q2PRO-X
работал, эта сессия была привязана к одной комнате. Для перехода в другую
комнату пользователь должен был полностью закрыть игру и повторно запустить
launcher.

Q2PRO-X 1.5 by ly от 2026-08-25 уже имеет подходящий штатный интерфейс:

- современный server browser со вкладками `q2servers.com`, `Favorites`, `LAN`
  и `Custom`;
- локальную адресную книгу `adr0..adr15` для `Favorites`;
- `cl_serverbrowser_custom_source` для составного списка `quake2://`;
- обычный Quake II `status` для получения hostname, mod, map, players и ping.

На проверенной пользовательской установке четыре PlayGround-сервера появились
в `Favorites` только из локальных `adr0..adr3`; изменения Q2PRO-X со стороны
maintainer не потребовались. Следовательно, базовая интеграция Dos.Zone также
не требует модификации Q2PRO-X или участия его maintainer.

Подтверждено на exact Q2PRO-X 1.5, SHA-256
`831f42dc96e3399a8a8737943d6fde752e11f5e5f48ffc5957537c4e66cbf71d`, что
клиент получает локальный HTTP Custom source, повторно читает его при
`Refresh`, а `status`, `getchallenge` и `connect` используют один UDP source.
Пустое состояние и последовательность Room A → Room B зафиксированы в
[ограниченной проверке exact клиента](../verification/2026-08-29-q2pro-x-live-custom-source.md).
Исследование составного `quake2://` source остаётся историческим сравнением,
а не текущим способом поставки.

`Favorites` использовать для Dos.Zone нельзя: это заняло бы пользовательские
слоты, смешало динамические комнаты с личными серверами и создало бы конфликт
владения конфигурацией. `Custom` уже даёт отдельную штатную поверхность.

## Решение

Целевое пользовательское подключение реализуется только через launcher-owned
**room hub** и вкладку `Custom` Q2PRO-X. Отдельный picker и single-room ветка
координатора удаляются, чтобы не поддерживать два интерфейса и два lifecycle.
Кандидат `1.0.0-rc14` использует общий многокомнатный gateway по
[дизайну shared runtime](../design/2026-09-03-shared-multiroom-gateway.md). До
прохождения всех live/package gates он остаётся кандидатом для проверки, а не
готовой публичной поставкой.

### Пользовательский сценарий

1. Пользователь запускает `Q2PRO-X — Dos.Zone` без предварительного picker.
2. Room hub получает готовые публичные Quake II комнаты и свежие RTC данные
   через те же Dos.Zone endpoints, которые уже использует launcher, и каждые
   15 секунд обновляет полный набор совместимых targets в пределах `256`.
3. Hub проверяет локальное наличие карты и для каждой совместимой комнаты
   создаёт отдельный loopback endpoint в общем gateway.
4. Только target, прошедший настоящий Quake II OOB `ping`/`ack`, появляется в
   локальном `Custom` source.
5. Q2PRO-X запускается один раз; его стартовое меню определяется обычной
   настройкой клиента.
6. Пользователь выбирает комнату обычным способом.
7. Для смены комнаты пользователь выполняет `Disconnect`, снова открывает
   browser и выбирает другую строку. Q2PRO-X не перезапускается.
8. При выходе из Q2PRO-X hub завершает общий gateway и временные данные.

```text
Q2PRO-X Custom source
  Dedicated A -> 127.0.0.1:31001 -> shared gateway -> Dos.Zone Dedicated A
  Room A      -> 127.0.0.1:31004 -> shared gateway -> Dos.Zone Room A
```

Hub отдаёт Q2PRO-X только loopback endpoints. Он не генерирует synthetic
Quake II status. Browser отправляет обычный status-запрос на выбранный
loopback endpoint, gateway передаёт его в настоящую комнату, а Q2PRO-X получает
фактические hostname, mod, map, players и end-to-end ping.

Если при запуске комнат нет, Q2PRO-X всё равно один раз запускается с пустым
списком `Custom`. Launcher не выводит предварительное сообщение об отсутствии
комнат и не завершает работу. Новая комната появляется после следующего
успешного опроса каталога, readiness шлюза и обычного `Refresh` пользователя.

### Custom source contract

Hub поднимает один локальный HTTP-источник только для текущей сессии и передаёт
его стабильный URL через `cl_serverbrowser_custom_source`:

```text
+set cl_serverbrowser_custom_source http://127.0.0.1:<source-port>/servers
```

`GET /servers` возвращает `200 OK` и тело из строк вида
`127.0.0.1:<udp-port>`. В тело попадают только готовые, нетерминальные шлюзы;
учётные данные и внешние адреса Dos.Zone туда не попадают. Источник закрывает
соединение после ответа и не пишет данные на диск. Начальное состояние может
быть пустым.

Принятый live scope — все совместимые комнаты в пределах `256` targets — и
правила переходов:

- список не делится на квоты `q2`/`q2ded`;
- превышение `256` targets завершается явной ошибкой, а не молчаливым
  усечением;
- каталог опрашивается раз в 15 секунд;
- target удаляется после двух последовательных успешных опросов, в которых
  комната отсутствует;
- ошибка каталога сохраняет текущие targets и не публикует разрушительное
  обновление;
- существующий target сохраняется для комнаты, даже если она заполнена, пока
  `roomReady` остаётся истинным;
- новая переполненная комната не публикуется;
- legacy `q2` сохраняет прежние правила отказа;
- сбой одного target не завершает Q2PRO-X и остальные targets;
- источник обновляется только существующей кнопкой `Refresh` Q2PRO-X.

### Поток управления launcher–coordinator

Launcher оставляет `stdin` координатора открытым и передаёт независимые
построчные команды для слотов:

```text
0 room.q2ded.server {compact room JSON}
3 room.q2.owner.generation {compact room JSON}
0 -
```

Контракт потока управления:

- первый байт — `0` или `1`, затем один ASCII-пробел;
- `-` означает пустой слот;
- непустая команда содержит заранее проверенный несекретный идентификатор
  комнаты, один ASCII-пробел и компактный JSON комнаты;
- JSON — одна строка UTF-8, созданная существующим компактным кодировщиком;
- размер команды не превышает 256 KiB;
- неверные UTF-8, номер слота, внешняя форма JSON, превышение размера или EOF
  после неполной строки — ошибка протокола с полной очисткой сессии;
- смыслово неверная конфигурация закрыто отклоняется только для ещё не
  опубликованного слота, её буфер очищается, а идентификатор комнаты заносится
  в tombstone;
- чистый EOF после полной строки означает исчезновение launcher/владельца и
  запускает полную очистку;
- launcher сохраняет точную строку JSON для комнаты, пока она остаётся в
  слоте, поэтому обновление ICE не перезапускает исправный шлюз;
- coordinator хранит только несекретный идентификатор комнаты и состояние
  жизненного цикла; каждый полученный JSON очищается сразу после передачи
  шлюзу, отклонения или игнорирования;
- после каждого успешного опроса каталога launcher посылает heartbeat для
  каждого требуемого слота; исправный неизменившийся шлюз его игнорирует;
- после сбоя, произошедшего после `TRANSPORT_READY`, для одного идентификатора
  разрешается не более одной повторной попытки; смысловой или предшествующий
  readiness сбой и
  неудачная повторная попытка заносят идентификатор в tombstone; счётчик
  повторов сбрасывается только при очистке или смене идентификатора;
- `ROOM_CLOSED` заносит слот и идентификатор в tombstone до очистки или замены
  другим идентификатором и не запускает известную закрытую комнату снова;
- Q2PRO-X получает null stdin, а не поток управления coordinator.

При каждом `Refresh` Q2PRO-X заново получает текущий текст `/servers`, поэтому
новые готовые комнаты и удаление закрытых комнат видны без перезапуска Q2PRO-X.
Hub не нажимает `Refresh` сам и не вводит команды в клиент.

Формат запроса источника:

```text
GET /servers HTTP/1.1
Host: 127.0.0.1:<source-port>
```

Успешный ответ имеет точную длину тела и закрывает соединение:

```text
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Cache-Control: no-store
Content-Length: <exact bytes>
Connection: close

127.0.0.1:31001
127.0.0.1:31002
```

HTTP-источник работает с ограничениями жизненного цикла:

- слушает только IPv4 `127.0.0.1` на порту, выбранном операционной системой;
- принимает только `GET /servers`;
- ограничивает заголовки запроса 8 KiB;
- закрывает каждое соединение после одного ответа;
- публикует только готовые нетерминальные шлюзы;
- хранит текст источника только в памяти и никогда не сохраняет учётные данные;
- использует один небольшой присоединённый поток и системные сокеты без
  дополнительной зависимости;
- использует неблокирующие сокеты, отдельный stop pipe/event и ограничение в
  одну секунду для неполного заголовка, чтобы остановка не зависала в
  `accept` или `recv`;
- при остановке сначала закрывает активного клиента, затем присоединяет поток;
  смерть listener после запуска считается конечной ошибкой coordinator.

Q2PRO-X запускается один раз с такими добавочными аргументами:

```text
+set game 3zb2
+set cl_timeout 20
+set cl_serverbrowser_custom_source http://127.0.0.1:<source-port>/servers
```

Q2PRO-X может сохранить несекретный loopback source штатным autosave. Add-on не
редактирует CFG и не меняет `cl_serverbrowser_default_source`: пользователь
видит обычное стартовое состояние клиента. Если после запуска видна консоль,
пользователь нажимает `Esc`, открывает `Join online` и выбирает вкладку
`Custom`, затем нажимает `Refresh`. Принудительный
`serverbrowser_open_modern` не используется. Diff изолированного профиля
остаётся release gate.

Существующие gateways захватывают первый loopback UDP source и отвергают второй.
Поэтому первая проверка должна доказать, что exact Q2PRO-X использует один и тот
же UDP source socket для `status` и последующего `connect`. Если это неверно,
реализация не должна ослаблять source isolation наугад: ADR возвращается на
пересмотр с фактической трассировкой пакетов.

### Общий и платформенный слои

Функция является общим продуктовым слоем, но не новым transport backend.

Общий контракт и одинаковое поведение на обеих платформах:

- получение и валидация каталога Dos.Zone;
- живое состояние пяти слотов и соответствие room ID → loopback UDP endpoint;
- стабильный loopback HTTP Custom source;
- пятнадцатисекундный опрос каталога и правила удаления/повторной попытки;
- правила readiness, refresh, room close и shutdown;
- redaction, exit reasons и acceptance tests.

Платформенные адаптеры:

- Windows запускает существующие WebView2 gateways и использует Job Object;
- Linux запускает существующие native WebRTC-NET gateways и использует process
  group/guardian;
- Windows запускает native `Q2PRO-X.exe`, Linux — тот же exe через Wine;
- установка и обнаружение Q2PRO-X остаются раздельными.

Существующий координатор на каждой платформе становится hub coordinator.
PowerShell и Python только собирают и валидируют состояние каталога; они не
становятся границей владения процессами.

### Lifecycle

Hub владеет одной запущенной Q2PRO-X и набором gateways. У каждого gateway свои
config/event/owner pipes и WebView2 directory. Windows использует корневой Job
Object для всей сессии и вложенный Job для дерева каждого gateway: закрытие
вложенного Job убирает только соответствующие gateway/WebView2 процессы. На
Linux у каждого gateway и Q2 отдельная process group; guardian
очищает весь набор по существующему session marker. Закрытие или падение одной
комнаты завершает только её gateway и не затрагивает Q2 и другие комнаты. При
закрытии активной комнаты Q2 остаётся запущен; соединение
завершается по штатному таймауту либо пользователь выполняет `Disconnect`,
после чего выбирает другую комнату.

Выход Q2, закрытие hub или crash владельца очищают весь принадлежащий add-on
process tree. Windows сохраняет `KILL_ON_JOB_CLOSE`, Linux — guardian. На каждую
WebView2-сессию используется отдельный user-data directory.

### Content compatibility

До публикации endpoint hub проверяет наличие требуемой карты существующим
content checker. Несовместимая комната не показывается в `Custom`; причина
попадает в redacted diagnostic log. Если совместимых комнат нет, Q2PRO-X всё
равно запускается один раз с пустым источником `Custom`; launcher не показывает
предварительное сообщение и не завершает сессию.

## Security invariants

- UDP gateway слушают только `127.0.0.1`.
- ICE/TURN credentials, SDP и candidates не попадают в source, arguments,
  environment, CFG или постоянные файлы. Linux compatibility gateway передаёт
  публичный room alias закреплённому legacy transport через `--alias`; его
  diagnostics проходят redaction перед выводом. Windows managed gateway получает
  весь room config через stdin.
- Fresh room configuration передаётся каждому gateway только через stdin.
- В source нет room credentials и внешних адресов Dos.Zone — только loopback.
- Hub ограничивает размер и схему внешнего каталога и готовит не более пяти
  gateway.
- Installer не занимает `adr0..adr15`, не создаёт `servers.lst` и не изменяет
  Favorites пользователя.

## Не входит в решение

- изменение `Q2PRO-X.exe` или добавление отдельной вкладки силами maintainer;
- создание или администрирование комнат Dos.Zone;
- browser/portal automation;
- synthetic server status или фиктивные player rows;
- общий внешний UDP gateway;
- оптимизация нескольких комнат в один WebView2/native transport process до
  появления измеренной проблемы ресурсов.

## Альтернативы

### `adr0..adr15` / Favorites

Технически работает и подтверждено текущей установкой, но занимает личные
слоты, имеет лимит 16 и смешивает владельцев конфигурации. Отклонено.

### `servers.lst`

Не требует HTTP listener, но требует писать внутрь virtual filesystem Q2,
смешивает комнаты с Favorites и хуже обновляется во время работы. Отклонено.

### Отдельный room picker и `+set game 3zb2 +connect`

Удалён из текущего кода. Он сохраняется только в исторических rc8 artifacts:
два режима создавали бы лишнюю поддержку и разный пользовательский опыт.

### First-class provider внутри Q2PRO-X

Дал бы отдельную вкладку `Dos.Zone`, но требует изменений и поддержки другого
проекта. Для базовой интеграции не нужен. Может быть рассмотрен позже без
изменения room-hub transport architecture.

### Один многокомнатный gateway

Уменьшил бы число процессов, но потребовал бы новый multiplexing contract и
изменение уже проверенных gateways. Отложен до измеренного resource bottleneck.

## Последствия

Положительные:

- комнаты Dos.Zone становятся обычными серверами в знакомом интерфейсе;
- Q2PRO-X запускается один раз и переключает комнаты без restart;
- Favorites и обычный shortcut игры остаются независимыми;
- реальные server status и ping не подменяются;
- Windows и Linux сохраняют один пользовательский контракт.

Компромиссы:

- вместо нескольких gateway используется один shared gateway runtime;
- room hub становится долгоживущим владельцем Q2 и общего gateway;
- перед распространением нового live-hub candidate нужны exact runtime и
  resource gates.

## Обязательные gates

1. **Custom source:** exact Q2PRO-X получает с одного стабильного
   `http://127.0.0.1:<source-port>/servers` сначала пустой список, затем Room A
   и Room B после обычного `Refresh`; Q2PRO-X не перезапускается, а diff
   normal-exit/crash профиля ограничен штатным autosave и несекретным
   loopback source.
2. **Real status:** dedicated и обычная комната одновременно показывают фактические hostname,
   mod, map, players и измеренный через transport ping без synthetic response;
   packet trace подтверждает один UDP source для `status` и `connect`.
3. **Switch:** Q2 входит в Room A, выполняет `Disconnect`, затем входит в Room B
   без завершения процесса Q2PRO-X; движение и выстрел видны владельцу Room B.
4. **Room close:** закрытие активной и неактивной комнат завершает только
   соответствующий gateway; Q2 и второй gateway остаются живы, после чего
   выполняется вход во вторую комнату.
5. **Lifecycle:** normal exit, Q2 crash, gateway crash и hub hard-kill не
   оставляют gateway, WebView2/Wine или session data.
6. **Security:** source, args, env, CFG и redacted logs не содержат room/ICE
   credentials.
7. **Resources:** Windows и Linux измерены при mixed `q2`/`q2ded` targets;
   список не усекается молча, а `256+` проверяется как явная ошибка.
8. **Packaging:** portable/setup/Linux package проходят smoke и live switch
   именно из заново распакованных release artifacts.

До прохождения gates 1–8 live-hub candidate не считается готовым к широкому
распространению. Текущие статусы и отделение компонентной
проверки exact клиента от проверки поставки приведены в
[`1.0.0-rc14 verification`](../verification/1.0.0-rc14.md). Rollback — это
возврат к предыдущему проверенному архиву; gateways и transport backend при
этом не меняются.
