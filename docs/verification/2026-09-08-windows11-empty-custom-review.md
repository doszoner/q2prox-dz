# Windows 11: пустой Custom — проверка пользовательского архива

Дата: 2026-09-08. Первичная диагностика по `5db6275`, до исправлений.
После этого пользователь разрешил реализацию; её отдельные результаты
фиксируются в [Windows rc16 verification](1.0.0-rc16.md).

## Вывод

Есть достаточные основания исправлять наш Windows add-on, а не рекомендовать
переустановку Windows, отключение защиты или изменение серверов. Три механизма
из внешнего отчёта воспроизведены на текущем коде; дополнительно подтверждено
несоответствие terminal-event протокола gateway/coordinator. Успешная работа
после предложенных пользователем правок НЕ доказана.

Проверка внешнего ревью велась с независимым сопоставлением текста отчёта,
сырых материалов, исходников и реальной portable-поставки. Это позволило
отделить воспроизводимые дефекты от неподтверждённого объяснения про серверы.

## Подтверждённые механизмы

### 1. Одна отсутствующая карта прерывает построение всего списка

`windows/product/catalog.ps1:497` бросает `map content check failed` при первой
недоступной карте. `Get-Q2DzLiveTargets` передаёт исключение наверх;
`Start-Q2DzLauncher` (`q2dz-launch.ps1:365`) подавляет его и начинает с пустым
набором целей. Следующий опрос не поможет, пока тот же набор продолжает
вызывать ошибку.

В архиве `q2dm1` и `q2duel1` проходят content-check, `q2ctf2` возвращает 3.
По `content_check_main.cpp` это CONTENT_MISSING. Это означает, что checker
не нашёл карту в выбранных `3zb2`/`baseq2`, а не доказывает её отсутствие
во всех каталогах компьютера. Checker не ищет произвольную папку мода CTF.

Реконструированы шесть строк из `logs/03-room-catalog.txt`, к ним применены
исходы проверки карт из `logs/10-content-check-per-map.txt`:

```text
BASELINE 6 valid rooms, 1 unavailable map: map content check failed; no plan returned
Get-Q2DzLiveTargets with captured map outcomes: map content check failed
Proposed new-target skip, same 6-row snapshot: targets=5
Proposed patch, retained target rotates to missing map: map content check failed
```

Правка `throw` → `continue` для новых целей действительно изолирует этот
случай. Но `catalog.ps1:488` сохраняет общую ошибку при смене карты уже
существующей цели. На обновлении код сохраняет прежнее состояние, а не
немедленно очищает список. Это различие важно: одного `continue` недостаточно,
нужно определить судьбу конкретной неподдерживаемой цели, не ломая остальные.

Действующие тесты намеренно проверяют сохранение старого состояния при
ошибке карты. Изменение политики требует согласованного изменения тестов,
а не механического удаления всех `throw`.

### 2. Ротация ICE пересоздаёт комнаты

`q2dz-launch.ps1:183` включает ICE в JSON комнаты, `catalog.ps1:486` сравнивает
весь JSON как строку, `:491` добавляет DROP при любом изменении. Heartbeat
посылает DROP, затем PUT. При изменении только ICE в fixture:

```text
ICE-only change: targets=5, drops=5
```

Пользовательский лог показывает два различных epoch-префикса с интервалом
три секунды. Это доказывает изменение ответа между запросами, но не точный
период ротации credentials. Полной временной записи «мигания» `/servers` нет.

Удаление ICE из per-room config может устранить сравнение: основной HUB-путь
передаёт ICE отдельно. Предпочтительный ориентир — уже существующий Linux
код `linux/tools/q2dz-launch:548`: исключать ICE из решения о пересоздании,
сохраняя независимое обновление ICE. Проверить также fallback в
`Invoke-Q2DzHub`, который умеет получать начальный ICE из конфига цели.

### 3. Реальный JS-отправитель несовместим с C++-приёмником UDP

`windows/gateway/assets/transport.html:367` создаёт объект в порядке
`type, data, targetId`. `windows/gateway/src/webview_bridge_protocol.cpp:207`
требует точный префикс с порядком `type, targetId, data`.

Выполнена фактическая строка отправителя с `bytesToMessage`, результат
JSON-сериализации подан в настоящий C++ decoder:

```text
JS message 0: invalid tagged datagram message
JS message 1: accepted
```

Второе сообщение отличается только предложенным в архиве порядком полей.
Это подтверждённая несовместимость, не проблема драйвера или Windows 11.
Исключение в обработчике WebView (`main.cpp:575`) вызывает
`fail("invalid_web_message")`: повреждается не только ответ одного сервера,
а работа общего шлюза.

### 4. Исходная причина FATAL скрывается ошибкой протокола

Gateway `windows/gateway/src/main.cpp:1127` выдаёт
`Q2DZ/HUB/2 FATAL stage=gateway code=...`. Координатор
`windows/coordinator/src/child_protocol.cpp:461` принимает READY, CLOSED,
FAILED, HEARTBEAT, но не FATAL. Прямая проверка его parser:

```text
Gateway FATAL -> coordinator: unknown HUB/2 event
```

Это точный текст из `logs/session-stderr.txt`. Возможная цепочка:
несовместимый UDP JSON → invalid_web_message → HUB/2 FATAL → unknown HUB/2
event → очистка `/servers` и восстановление gateway. После исчерпания
единственного общего перезапуска транспорт отключается, Q2PRO-X остаётся.
См. `windows/coordinator/src/windows/main.cpp:1143` и `:1307`.

Несоответствие протокола доказано. Что именно вызвало FATAL в конкретном
запуске пользователя, не установлено: исходная строка gateway отсутствует,
а порядок и время применения правок относительно ошибки неизвестны.
Нужно согласовать terminal-event контракт и сохранять безопасные stage/code;
нельзя просто молча игнорировать неизвестные события.

## Что в присланном отчёте нельзя принять как доказанное

1. «21/21 OK» противоречит `logs/02-sha256-verification.txt`: там 19 OK,
   два mismatch (`transport.html`, `q2dz-launch.ps1`). Проверки после всех
   трёх правок нет; исходное «до правок всё совпадало» данными не подтверждено.
2. Из шести перечисленных комнат после исключения CTF остаётся пять,
   а не шесть. Локальная реконструкция даёт пять. Более поздний каталог мог
   измениться, но его строки/roomId и время в архиве не сохранены.
3. `logs/09-live-chain.txt` содержит пустое поле UDP_ENDPOINT, TCP listener
   и два UDP-сокета, но не HTTP body `/servers`, READY-события, hex запросов,
   ответы или таймауты. Он не доказывает опубликованный рабочий endpoint.
4. Target count и `HasConfig=True` доказывают только построение плана,
   не готовность WebRTC, видимость в Custom или вход на карту.
5. «Хост — вкладка в фоне» не установлено: перечислены q2ded, не браузерные
   q2 комнаты. Значения foreground/fps без контракта источника и серверных
   логов не доказывают остановку dedicated-процесса.
6. Если UDP-проверки действительно отправляли буквальные `getinfo`/`getstatus`,
   они не соответствуют обработчику нашего Quake II: тот понимает `info`
   с версией протокола, `status` и `getchallenge`
   (`quake2/server/sv_main.c:2205`, `:1004`). По отсутствующим байтам нельзя
   установить правильность этих проб. Отсутствие ответа на getchallenge
   тоже требует реального endpoint и транспортных данных.
7. Сбой `room catalog has an invalid schema` зафиксирован, но «временная
   невалидная строка» — лишь объяснение автора: исходного payload нет.
   При этом несогласованность валидаторов воспроизводится: одна некорректная
   поддерживаемая строка отвергает весь payload, а Get-Q2DzReadyRooms пропускает
   её и возвращает пять годных строк. Ослаблять проверку корня, дубликатов,
   размера и безопасных значений на этом основании нельзя.

## Что сказать пользователю и что делать у нас

Сообщение пользователю:

> Логи выявили ошибки в нашем Windows-дополнении. Каталог серверов у вас
> загружается, версия Q2PRO-X соответствует поддерживаемой. Одна недоступная
> CTF-карта может скрывать остальные серверы; есть также ошибки обновления
> комнат и шлюза. Оснований переустанавливать Windows или отключать защиту нет.
> Нужна проверенная исправленная поставка. Пока сохраните изменённые файлы и,
> если повторяете запуск, укажите время и пришлите полный session stderr,
> безопасные gateway события и снимки локального /servers из этой же сессии.

Наличие корректного CTF-контента в выбранном игровом пути может обойти только
первую проблему, но не исправляет шлюз и ICE. Не предлагать переименовывать
другую BSP в q2ctf2 или отключать content-check/валидацию целиком.

Приоритет у нас: исправить JS/C++ обмен и ICE-сравнение; согласовать
покомнатную политику content failure для новых и существующих целей; исправить
диагностику terminal events и подавленных ошибок launcher. Затем новая
версионированная Windows-поставка с обновлёнными SHA256SUMS и реальным E2E.
Три текстовых патча из архива без этих проверок не являются готовым релизом.

Дополнительное замечание о поставках: отдельно проверенный файл
`../q2prox-dz-full-20260906-114237.zip` содержит в корне исходников VERSION
`1.0.0-rc12` и старые Windows-файлы. Это не проверенный здесь portable rc15.
Нельзя определять актуальность исходников лишь по дате имени внешнего ZIP
или предполагать, что у пользователя то же дерево без commit/diff.
