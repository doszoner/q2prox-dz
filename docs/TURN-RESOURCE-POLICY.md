# TURN: нагрузка шлюза и необходимые ограничения

Статус на 2026-10-18: выбор RTC реализован в исходниках, проверен компонентно
на Python/PowerShell Core. Windows PowerShell 5.1 и обычный Hub ещё не проверены.
**Ограничение одновременных соединений не реализовано.** Производственные квоты
и фактические аллокации не измерялись.

## Что делает текущий шлюз

- Linux `_ice_snapshot` в [launcher](../linux/tools/q2dz-launch) и Windows
  `Get-Q2DzDedicatedIceServers` в [catalog.ps1](../windows/product/catalog.ps1)
  выбирают все ICE-записи одной строки и TURN/TURNS URL второй, с семантической
  дедупликацией. Сессионный кэш хранит domain, credentials берутся заново.
- [Native transport](../linux/transport/q2_doszone_gateway.cpp),
  `process_resolutions`/`process_probes`, и [WebView2 transport](../windows/gateway/assets/transport.html),
  `allocateTargetRoute`/`resolveTargets`, последовательно разрешают маршруты
  и поддерживают соединения с доступными targets. Очередь разрешения алиасов
  ограничивает одновременную работу этого этапа, а не число уже открытых соединений.
- `max_targets=256` ограничивает размер каталога. Это не защита квоты TURN.
  Таймера вытеснения исправных неактивных соединений сейчас нет.
- Публикация в `Custom` требует готового транспорта и probe/ack. Q2PRO-X
  запрашивает status у показанных серверов при Refresh. Поэтому замена
  «подключаться сразу» на «подключаться при первом UDP-пакете» сама по себе
  снова откроет соединения со всем списком. См. [ADR 0004](adr/0004-q2pro-x-custom-source-room-hub.md).
- DROP закрывает маршрут через runtime; это видно в исходниках. Доказательств
  утечки аллокаций нет. Фактическое освобождение на TURN после штатного закрытия
  и аварии — отдельное измерение, а не следствие наличия вызова disconnect.

Транспорт закреплён в [deps.lock.json](../deps.lock.json) на WebRTC-NET
`62fe52cd20bae55baf03339afee60c895f1aee90`. Выводы о поведении другого checkout
или новой libwebrtc нельзя автоматически переносить на эту зависимость.

## Что именно считать

STUN Binding не создаёт TURN allocation. Relay-кандидаты собираются посредством
TURN; число ICE URL, кандидатов и открытых PeerConnection — разные величины.
Число реальных аллокаций зависит от транспорта, интерфейсов, реализации и
жизненного цикла ICE. Счётчик кандидатов не заменяет серверный счётчик аллокаций.
[ICE, RFC 8445 §5.1.1.2](https://www.rfc-editor.org/rfc/rfc8445.html#section-5.1.1.2).

В coturn `user-quota` ограничивает аллокации пользователя, `total-quota` —
общий предел сервера; ограничения полосы задаются отдельно. При общих
временных TURN-учётках несколько игроков могут конкурировать за одну user-quota.
Нельзя считать один username одним игроком. Значения из `.env.example` или
шаблона соседнего сервиса не доказывают действующую production-конфигурацию.
[Описание coturn](https://github.com/coturn/coturn/blob/master/examples/etc/turnserver.conf).

Для каждой квотной области сервера отдельно нужны текущие и пиковые аллокации,
отказы и скорость создания/закрытия. Локальные соединения шлюза — только часть
нагрузки: удалённые peers тоже собирают кандидаты, есть другие игроки и приложения.
Сумму URL разных серверов нельзя сравнивать с user-quota одного из них.
Поэтому прежнее утверждение «8 комнат × 18 URL = 144 аллокации при квоте 128,
один игрок гарантированно исчерпал её» удалено как недоказанное.

## Минимальные направления исправления

1. **Сократить список ICE-серверов.** Ближайший по измерению TCP сервер и TURN
   второго реализованы в [OpenSpec change](../openspec/changes/q2prox-nearest-turn/proposal.md).
   Это сокращает предлагаемые relay endpoints, но не обещает фиксированного
   снижения аллокаций и не ограничивает число соединений. Второй сервер может
   собирать кандидаты сразу; это не обязательно холодный резерв.
2. **Ограничить соединения и темп их открытия.** До реализации задать предел
   одновременно открытых/открываемых соединений, срок хранения неактивных,
   очередь discovery и задержку повторных попыток. Активная игровая связь не
   должна вытесняться просмотром списка. Конкретные числа выбрать по измерению
   обеих платформ и согласованной доступной квоте, а не по размеру каталога.
3. **Согласовать это с `Custom`.** Сначала решить, как показывать доступность
   комнат при ограниченном discovery, не выдавая непроверенную запись за READY,
   не подделывая server status и не скрывая комнаты молча. Изменение этого
   контракта требует отдельного дизайна; текущий nearest-turn его не меняет.
4. **Прекращать ненужный расход.** DROP, выход и отменённое подключение должны
   закрывать соответствующие соединения; повторный refresh не должен их
   бесконечно пересоздавать. Ротация credentials сама по себе не освобождает
   allocations. TURN Refresh с lifetime=0 удаляет allocation; при аварии важен
   срок её истечения. [RFC 8656 §8](https://www.rfc-editor.org/rfc/rfc8656.html#section-8),
   [RTCPeerConnection.close](https://www.w3.org/TR/webrtc/#dom-rtcpeerconnection-close).
5. **Не отвечать на квоту шквалом reconnect.** TURN 486/508 требуют политики
   повторов с задержкой; для обычного случая RFC рекомендует (SHOULD) ждать минимум
   минуту перед повтором к тому же серверу. Сначала проверить, какие причины
   отказа доступны через закреплённый WebRTC-NET; нельзя выдумывать 486 из
   общего `transport_failed`. [RFC 8656 §7.4](https://www.rfc-editor.org/rfc/rfc8656.html#section-7.4).

Не следует лечить проблему только увеличением серверной квоты: без ограничения
соединений расход продолжит зависеть от числа комнат и игроков. Но и клиентский
предел одного процесса не гарантирует соблюдение общей квоты всеми клиентами.

## Проверка будущей реализации

Короткие проверки на Linux и Windows: открытие списка, повторный Refresh,
вход в комнату, смена карты, выход, исчезновение комнаты и остановка launcher.
Сопоставить число активных/открываемых соединений и попыток с агрегированными
счётчиками TURN до, во время и после. Отдельно проверить аварийное завершение
и поведение по истечении allocation lifetime. Не создавать перегрузку production.

Для списка больше выбранного предела проверить соблюдение лимита и сохранение
активной игры. Если операторские метрики недоступны, результат ограничивается
клиентскими счётчиками; утверждать соблюдение серверной квоты нельзя.
Не публиковать username/credential, IP кандидатов, SDP, сырые RTC-ответы и логи.
Сохранять только обезличенные агрегаты и причины отказов из разрешённой грамматики.

В этой уборке проверены исходники и согласованность документов; сеть,
серверные метрики, нагрузка и gameplay не проверялись.
